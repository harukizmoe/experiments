# AGENTS.md

## 规范治理

本文件中的核心规则属于最高工程规范。

未经用户明确指示，不得修改、删除、弱化或通过重新解释规避这些核心规则。

项目特定规则可以在本规范基础上补充，但不得与核心规则冲突，也不得削弱核心规则。

当仓库变化导致项目特定指引失效时，可以对这些项目指引进行必要更新，但修改应保持最小范围，仅用于恢复其准确性。

## 核心哲学

使用能够完整解决真实问题的最小一致方案。

优先选择简单、清晰、正确的实现，而不是聪明、灵活或具有形式感的架构。

尽量减少概念、状态、间接层、依赖和隐藏行为。

不要追求更少的代码行数，要追求更低的认知复杂度。

遵循语言自身的惯用设计，不要把其他语言的模式机械移植过来。

问题没有证明复杂度的必要性之前，不要引入复杂度。

## 设计

在真正的抽象出现之前，保持实现具体。

只有在以下情况下才引入抽象：

* 表达真实的领域或系统概念；
* 保护重要的不变量或语义边界；
* 隔离已经存在的变化；
* 显著减少调用方需要理解的知识。

不要因为代码看起来相似，或未来可能出现变化，就提前抽象。

宁可保留少量重复，也不要制造错误抽象。

好的抽象消除调用方的复杂度；坏的抽象只是移动复杂度。

优先围绕稳定语义设计，而不是追求通用机制。

没有真实需求时，不要引入接口、工厂、注册表、扩展点、额外分层或框架。

优先使用少量强大且可组合的基础能力，而不是大量专用机制。

核心尽量提供机制；策略和可选行为尽量留在边缘。

优先显式控制流和可见副作用，避免魔法、隐式注册、隐藏状态修改和不必要的间接调用。

保持设计浅层。每增加一层，都应真正改变语义、保护不变量或消除复杂度。

## 状态

尽可能缩小系统的状态空间。

能够低成本且可靠推导出的值，不要额外保存为状态。

优先保持单一事实来源，并明确区分权威状态与派生状态。

尽量让非法状态无法表达。

互斥状态应直接建模为互斥状态，而不是多个独立布尔值。

重要状态转换必须有清晰的所有者和明确的转换路径。

并发会扩大状态空间。只有收益足以抵消额外推理成本时才引入并发。

每个并发任务都必须有明确的所有者和结束路径。

## 修改原则

修改之前先理解现有设计。

选择能够完整解决问题的最小一致变更，而不是单纯追求最小 diff。

不要进行与当前需求无关的重构。

除非现有约定本身就是问题，否则保持项目已有风格。

如果现有结构导致一个正确修改变得不必要地复杂，可以进行最小范围的局部重构，使设计重新变得简单。

没有真实需求时，不要增加兼容层、fallback、特殊分支、配置项或扩展点。

语言、标准库、运行时、操作系统或项目现有基础能力已经能够良好解决的问题，不要重复实现。

## 代码质量

代码首先应该通过结构和命名解释自己。

优先直接、普通、容易推导的代码，而不是聪明的表达式。

注释主要解释为什么：不变量、外部约束、非显而易见的决策，以及看起来可能像偶然行为的设计。

不要用注释弥补本可以变得更简单的代码。

依赖本身就是复杂度。只有长期收益明显高于成本时才增加依赖。

高级语言特性只是工具，不是目标。只有当它们确实让设计更简单时才使用。

## 验证

验证外部行为和重要不变量，而不是实现细节。

修复 Bug 时，在合适的情况下增加聚焦的回归测试。

先运行最相关、范围最小的检查，再执行项目要求的完整验证。

不要为了让修改通过而削弱测试、类型约束、校验逻辑或系统不变量。

## 项目事实

能够从当前仓库可靠获取的易变信息，不要在本文件中重复维护。

命令、依赖、目录结构、运行环境等项目事实，应以源码、构建配置、包管理配置、依赖清单和 CI 配置为事实来源。

能够直接从仓库确认的信息，应检查当前仓库，而不是依赖可能已经过时的文字说明。

如果当前修改使项目文档或 Agent 指引失效，应在同一次修改中同步更新。

只有无法从仓库本身可靠推导、且确实影响工程决策的重要约束，才应记录在本文件中。

## 项目规则

确有必要时，可以在此补充项目特定约束。

项目规则应保持精简、明确并与当前项目状态一致。

已经能够通过代码、配置、测试或 CI 表达的信息，不要再次重复。

底层约束发生变化时，应同步更新或删除对应的项目规则。

项目规则不得与上述核心规范冲突，也不得削弱核心规范。

### Agent skills

#### Issue tracker

问题与规格文档使用 GitHub Issues 管理，通过 `gh` CLI 操作。详见 `docs/agents/issue-tracker.md`。

#### Triage labels

使用默认 triage 标签：`needs-triage`、`needs-info`、`ready-for-agent`、`ready-for-human`、`wontfix`。详见 `docs/agents/triage-labels.md`。

#### Domain docs

本项目采用单上下文布局，使用根目录 `CONTEXT.md` 与 `docs/adr/`。详见 `docs/agents/domain.md`。

### 项目定位

本目录（`go/`）是实验主仓库的 Go 部分：Go 语言实验场，通过相互独立的实验学习和验证网络编程、并发编程、I/O、运行时、性能等主题。实验之间默认没有业务关系，不应为了复用建立隐式耦合。

其他语言的实验在仓库根目录，不在本目录；本目录不新增第二个 Go module（module 路径 `harukizmoe/experiments/go`）。

### 架构布局

单一 Go module，所有实验位于 `experiments/` 下，每个实验是可独立运行的 `package main`：

```text
go/
├── go.mod
├── AGENTS.md
├── CONTEXT.md
├── docs/
└── experiments/
    └── <experiment-name>/
        ├── README.md
        ├── main.go
        └── *_test.go
```

不要预先创建空目录、共享工具包或抽象层。一个实验只有在实际需要时才添加额外源文件和目录。

### 实验约定

- 实验目录使用简短、稳定、全小写的 kebab-case 名称，例如 `net-tcp`、`concurrency-worker-pool`。
- `main.go` 是实验入口；运行命令为 `go run ./experiments/<experiment-name>`。
- `*_test.go` 验证可重复的行为、边界条件、错误路径和并发安全性；优先使用表驱动测试与子测试。
- `README.md` 使用中文，说明实验目的、待观察的问题、关键概念、运行命令、预期现象和结论。
- 实验不得直接导入其他实验目录。
- 只有至少两个实验实际需要相同领域行为时，才提取共享模块；共享模块必须拥有小而清晰的接口和独立测试。
- 实验代码中的注释解释原因、生命周期和并发约束，不重复翻译代码。

### 注释规范

- 面向初学者编写实验代码中文注释：不仅说明代码做什么，还要说明为什么这样做，以及它在整个实验流程中的位置。
- 关键的结构定义、类型字段、常量、导出或核心函数必须有注释，解释数据含义、生命周期、调用关系和约束。
- 涉及 Context、goroutine、channel、Span、Trace、队列、序列化、资源关闭或错误传播时，必须说明上下文如何传递、所有权归属、退出条件和失败影响。
- 复杂逻辑按代码执行顺序添加教学式行内注释，尽可能让初学者可以仅阅读源码理解关键步骤；不要机械注释显而易见的赋值、加法或标准库调用。
- 跨进程、网络协议、第三方 API 等边界必须解释输入输出格式、关键字段和与本实验目标的关系。
- 如果实现采用了简化模型，必须写明适用范围和已知限制。
- 修改代码时同步更新已过时的注释，禁止保留与实际行为不一致的教学说明。

### 依赖策略

- 标准库优先；能用标准库清晰解决的问题不引入第三方依赖。
- 第三方依赖按实验引入，不为未来实验预先添加依赖。
- 使用第三方依赖时，在对应实验的 `README.md` 中记录用途、版本和选择原因。
- 实验专属依赖不得通过共享包间接泄漏给其他实验。

### Go 编码与并发规范

- 修改 Go 代码后运行 `gofmt`，并使用 `go vet ./...` 检查。
- 所有错误都必须显式处理；上下文信息使用 `fmt.Errorf("...: %w", err)` 保留原始错误。
- 不使用 `panic` 处理正常运行时错误；仅在不可恢复的程序员错误或实验明确研究 panic 时使用。
- 阻塞操作应接收并响应 `context.Context`；取消、超时和关闭路径必须可验证。
- 每个 goroutine 都必须有明确的启动条件、退出条件和错误传播路径；禁止产生无法回收的 goroutine。
- channel 的所有权、关闭责任和缓冲策略必须明确；避免通过共享可变状态传递结果。
- 网络连接、文件、ticker、timer 和其他资源必须在拥有者处释放。
- 只有在有可测量证据时才优化分配、锁竞争或吞吐；性能实验应附带 benchmark 或明确的测量命令。

### 测试与验证（Go）

- 新增可观察行为时，必须添加能在合理缺陷下失败的测试；不要测试实现细节。
- 并发实验必须运行 `go test -race ./...`；涉及性能时补充 `go test -bench=. -benchmem ./experiments/<experiment-name>`。
- 完成修改后至少验证受影响实验的运行命令和对应测试；涉及公共结构时再运行 `go test ./...` 与 `go vet ./...`。
- 实验 README 的预期现象必须与实际运行结果一致；不确定的结论标记为待验证，不伪造结果。

### 变更边界

- 优先保持实验局部性；不要在无关实验中顺手重构或统一风格。
- 添加共享代码前先证明存在两个真实调用方，并说明共享模块的接口、收益和测试边界。
- 设计模块时优先小接口、深实现和清晰 seam；调用方与测试都通过同一接口验证行为。
- 所有项目文档和注释使用中文；Go 标识符、命令、标准库名称和外部项目名称保留原文。

## 决策准则

当多个方案都正确时，优先选择：

1. 概念更少；
2. 状态更少；
3. 分支更少；
4. 依赖更少；
5. 间接层更少；
6. 更容易局部推理；
7. 行为更容易直接从代码中推导出来。

无法确定时，保持简单，保持具体。
